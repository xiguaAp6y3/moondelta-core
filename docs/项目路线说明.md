# moondelta-core 项目路线说明（0.4.0 本地工作区）

> 本文回答三个问题：项目走到了哪里、为什么这样设计、接下来去哪里。
> 配套文档：[ROADMAP.md](ROADMAP.md)（目标协议与冲刺排期）、[协议兼容性与互操作范围.md](协议兼容性与互操作范围.md)（口径与验收门槛）、[使用说明.md](使用说明.md)、[测试说明.md](测试说明.md)。历史文档 `开发计划.md` 是 2026-10-18 的首个六天排期，保留作起点记录。

## 1. 项目是什么

moondelta-core 是 MoonBit 的 Delta Lake 表格式内核：把"一批 Parquet 文件"升级为"带事务日志的表"——版本、快照、时间旅行、原子提交。当前版本在 **reader v1 / writer v2** 约束下交付**已验证子集**：嵌套 schema（struct / 标准 3-level list / map）读写、checkpoint 恢复，以及在指定 flat/nested fixture 上与 delta-rs 1.6.6、DuckDB 的双向对拍。该结果不等同于任意 reader v1 表的完整兼容；现行能力边界见 README。

## 3. 架构与模块地图

```
src/
├─ types.mbt       Delta 类型（含嵌套子树）/ 协议 / 快照 / DeltaError 四类错误
├─ actions.mbt     日志 action 解析（含 feature 列表、txn、percent-decode）
├─ log.mbt         日志文件枚举（20 位严格校验）、读写原语（write_text_new = put-if-absent）
├─ snapshot.mbt    回放状态机：完整日志从头回放；不完整日志从 checkpoint 恢复基底
├─ scan.mbt        文件级扫描规划（分区等值 + min/max 剪枝）
├─ read.mbt        数据读取入口（扁平路径）+ Cell 表示与渲染
├─ shred.mbt       M2：叶级槽位流 → struct/list/map 装配（读侧 shredding）
├─ checkpoint.mbt  M3：checkpoint parquet 逐记录解析（兼容 Spark/delta-rs 两种可空性标注）
├─ write.mbt       create_table / append_rows（防护 + 校验 + intent/提交顺序）
├─ writenested.mbt M4：Cell 列 → 叶级槽位流 + schema 树（写侧 shredding）
├─ txn.mbt         S2：txn ID、持久 intent、摘要校验、只读事务查询
├─ recover.mbt     S3：dry-run/apply 恢复、受管策略、历史/checkpoint 保护
├─ sha256.mbt      FIPS 180-4 SHA-256（纯 MoonBit，全目标可编译）
├─ atomic_file.mbt / atomic_file_native.c  预固定临时名发布、文件/目录同步、POSIX flock / Windows LockFileEx
├─ json_util.mbt   JSON 访问小工具
├─ vendor/parquet/ vendored mizchi/parquet@0.2.2 + 扩展：
│    shredded.mbt（嵌套读取：叶级"值+def/rep"槽位流）
│    writer_shredded.mbt（嵌套写入：schema 树 + 槽位流 → parquet）
│    （另修复 def level 递增规则：OPTIONAL 与 REPEATED 都递增）
├─ cmd/delta/      CLI（inspect/history/scan/read/create/recover/query/manage/version）
└─ examples/       read_covid / interop_flat_writer / write_nested / write_all_types / atomic_commit_worker
```

## 4. 关键设计决策

1. **闭集 + 结构化拒绝**：支持范围内 100% 有测试；范围外一律 `DeltaError`（Io/Parse/Unsupported/NotFound）+ 原因，CLI 层 stderr + 非 0 退出。宁可拒绝，不返回错数据。
2. **shredded 读写对称**：vendored reader/writer 只负责"叶级槽位流"（值 + def/rep levels），记录的装配/拆分放核心层按 Delta schema 树完成——嵌套逻辑集中在一处（shred.mbt / writenested.mbt 互为镜像），vendor 改动最小且边界清晰（NOTICE 记录）。
3. **checkpoint 解析不依赖声明式 schema**：不同 writer（Spark 经典 / delta-rs）对列可空性标注不同，解析按叶列实际 def/rep levels 逐记录进行，以规范必填标量（add.path 等）判定 action 是否出现；未解释列按记录消耗槽位保持游标同步。
4. **恢复只在不完整日志时启用**：完整 JSON 日志永远从头回放（历史/时间旅行语义稳定），checkpoint 恢复仅用于顶端截断或 checkpoint-only 表——`checkpoint-truncated` 因此从静默读旧版本（v9/90）修复为正确恢复（v10/100/100）。
5. **绝对不允许静默**：未知 action、stats 损坏、未知 CLI 参数等要么报错、要么显式记录并提示（`Snapshot.ignored_actions`）。

## 5. 当前能力与显式例外

支持闭集：reader v1 / writer v2；全部 primitive + 嵌套读写；SNAPPY/UNCOMPRESSED；本地文件系统；单文件经典 checkpoint 恢复；OS 随机事务 ID、持久 intent、结果查询、受管安全清理、POSIX/Windows 固定维护锁。显式例外（结构化拒绝并说明原因）：decimal、uuid；ZSTD/GZIP/BROTLI/LZ4；reader ≥ 2 特性（column mapping、deletion vectors、v2 checkpoint）；多部分 checkpoint；分区 append；MERGE/UPDATE/DELETE；对象存储。并发写只通过维护锁 + put-if-absent 返回冲突，不是通用事务仲裁。S5 掉电持久性未验收；Windows 仅声明进程崩溃一致性。
