# moondelta-core 项目申报书

## 基本信息
- 项目名称：moondelta-core —— MoonBit 的 Delta Lake 表格式内核
- 参赛者：xiguaAp6y3（GitHub）；项目方向：MoonBit 数据基础设施 / lakehouse 表格式
- GitHub 仓库：https://github.com/xiguaAp6y3/moondelta-core （申报期内建仓，D1–D6 以真实开发提交累积 ≥10 个有效 commit）
- 是否移植：否，原创实现；项目许可证：Apache-2.0

## 项目简介
MoonBit 这边，Parquet 读写（`mizchi/parquet`）、JSON、DataFrame（MoonFrame）、对 CSV/Parquet 跑 SQL 的引擎（moonlake）、Iceberg 只读（moonice）都有了，但"带事务日志的表"没有：没有版本、快照、时间旅行，也没有把一批 Parquet 文件原子提交成新版本的机制。结果是数据文件能读，表还得自己拼。

moondelta-core 补这一层：打开磁盘上的 Delta 表目录，回放 `_delta_log`，给出指定版本的文件清单，按分区和 min/max 统计剪枝，读数据文件，并在受支持的列类型上 append 提交新版本。通用性在于——只要 MoonBit 程序产出或消费 Delta 表，就能和 Spark、Databricks、delta-rs、DuckDB 交换数据；表格式是 lakehouse 的协议层，比单个查询引擎的复用面大。

## 一、价值与生态定位
具体问题是：在 MoonBit 里想增量入湖、想回滚到昨天的数据、想知道"这次提交改了哪些文件、影响多少行"，目前只能手写 JSON 解析加目录扫描，或者把这段逻辑绕去 Python/Spark。

查重：mooncakes 注册表 3,103 个模块里没有 Delta Lake / 表格式实现（`delta lake`、`lakehouse`、`table format`、`_delta_log` 四类关键词均 0 命中）。最近邻逐个划界：

- `moonice`：Iceberg v2 只读，不做 Delta，也不能写；
- `moonlake`：对 CSV/Parquet 跑 SQL 的查询引擎，没有表/版本/事务概念；
- `MoonFrame` 是 DataFrame，`magpiedb` 是嵌入式分析库，都不管表版本。

本项目的生态位是**事务日志层**——版本、快照、时间旅行、扫描规划、写入提交。不碰 Parquet 编解码（复用 Apache-2.0 的 `mizchi/parquet`，以 vendored 形式放进仓库），不碰 DataFrame，也不做 SQL 引擎。

## 二、交付范围与工程边界
交付：

- `Table::open(path)`、`Snapshot::at(v)`、`Table::history()`、`Snapshot::files()`；
- `_delta_log` 解析与回放：AddFile / RemoveFile / MetaData / Protocol / CommitInfo，识别 `_last_checkpoint`；
- 扫描规划：分区值过滤 + 文件 min/max 统计剪枝；
- 读：flat schema + UNCOMPRESSED / SNAPPY 的 Delta 数据文件；
- 写：append（写 Parquet 数据文件 + 提交新的 JSON 版本）；
- CLI `delta inspect | history | scan | read | create`、可运行示例（`src/examples/read_covid`）、核心路径测试、README、CI、发布 mooncakes.io。

明确不做，遇到就报错，不静默降级：

- 嵌套 schema（struct/list/map）和 ZSTD / GZIP / BROTLI 压缩：不支持，明确报错；
- checkpoint-only 表：只能从日志起始版本回放，日志被清理或截断时明确报错；
- 写入只覆盖 Int32 / Int64 / String / Binary（Required / Optional），不写 Boolean / Float / Double / Timestamp；
- 不做对象存储（MVP 只接本地 fs）、删除向量、列映射、checkpoint 写入、DataFrame / SQL 层。

## 三、实现路径与技术理解
三条路：① 包一层 delta-rs 或 Spark——MoonBit 没有 JVM/Rust 绑定，走不通；② 从 Parquet 往上自己造列存——重复造轮子；③ 只做协议层，复用现有 Parquet / JSON。我选 ③。

关键设计是 sans-IO 核心：日志解析、回放、扫描规划都是纯函数，输入字节或 JSON，输出文件清单，不碰文件系统和网络；测试可直接喂 delta-rs 的真实日志序列离线回放，不用起 Spark。文件系统和 Parquet 只在最外层做薄封装。

难点有三个：

1. 快照不是"读最后一个日志文件"，而是按版本顺序把 add/remove 叠起来；同路径 add 后再 remove、remove 后再 add 都要按时间收敛。我用"路径 → 最新状态"的 map 状态机做回放。
2. 协议版本的特性门控：`minReaderVersion` 超出支持范围要拒绝，不能猜。
3. 依赖的取舍：上游 `mizchi/parquet@0.2.2` 声明了 `mizchi/duckdb@0.6.4`，后者仍是旧版 `moon.mod.json`，最新 MoonBit 工具链（0.10.15）直接拒绝解析。这个依赖只被上游的 DuckDB 演示子包使用，所以我把 parquet 的 `src/` 以 Apache-2.0 **vendored 进仓库**，删掉两个演示子包、reader/writer 一行未改，并用 NOTICE 写清来源与修改。这样最新工具链可直接构建，CI 不需要 pin 版本。

一个我自己的判断：表格式的价值不是"多一个文件格式"，而是**把一堆不可变文件变成可版本化的状态机**。所以测试重点放在回放正确性——同一份日志回放两遍必须得到同一个文件清单——而不是先铺漂亮的 API。

## 预期使用场景
1. **MoonBit ETL 写出、Spark 直接读**：输入是清洗后的记录（Int64/String 列）；操作 `Table::open` + `append`，写 Parquet 并提交新版本；输出是标准 Delta 目录，Spark / Databricks / delta-rs 直接 `spark.read.format("delta")` 能读，MoonBit 侧不用懂 Spark。
2. **外部表校验与迁移**：输入 delta-rs 或 Databricks 产出的表目录（例如 COVID-19_NYT，157,865 行 6 列）；操作 `Snapshot::at(v)` + 扫描 + 读取，对比两个版本的文件清单和行数；输出校验报告或 CSV 导出，用于迁移前确认数据没缺、历史对得上。
3. **CI 数据契约审计**：输入仓库里随代码提交的小型 Delta 表和两个版本号；操作按版本回放，用分区和 min/max 统计剪枝算出被改动的文件；输出"这次提交改了 7 个数据文件、影响 12,480 行、落在 dt=2026-10-17 分区"的 Markdown 报告，作为 CI artifact。纯读路径，不需要写权限。
