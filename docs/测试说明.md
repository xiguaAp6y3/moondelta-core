## 2. 验收脚本

位置 `artifacts/acceptance/`：

```powershell
# Linux（WSL2 ext4；需 GCC、findmnt、Python 3 与 deltalake/pyarrow）
.tools/pyenv/Scripts/python.exe artifacts/acceptance/d2_verify.py          # 17 项：flat 双向对拍证据重算
.tools/pyenv/Scripts/python.exe artifacts/acceptance/d3_verify.py          # 40 项：nested 读取与 checkpoint 恢复
.tools/pyenv/Scripts/python.exe artifacts/acceptance/all_types_verify.py   # 11 种 primitive 外部回读

# 事务矩阵（Linux Native，本地文件系统）
python3 -m venv .venv && .venv/bin/pip install deltalake==1.6.6 pyarrow==26.0.0
.venv/bin/python -u artifacts/acceptance/test_atomic_commit_wsl.py --iterations 100 --output <results.json>

# Windows（Windows Native；标准库即可）
python artifacts/acceptance/test_transactions_windows.py --output <results.json>
```

`test_atomic_commit_wsl.py` 覆盖：20 个 syscall/intent 故障注入（含 intent 发布五阶段）、调用顺序、空批次、SIGKILL 残留与恢复、dry-run/受管 apply、历史保护、日志缺口、锁忙、未知文件保留、恢复 unlink 失败重试、writer 暂停在数据与 JSON 发布之间时的恢复器 busy、真实 remove 与 checkpoint 保护、checkpoint-only、软链接、真实 commit-unknown 查询、100 轮发布前竞争/连续 reader/冲突重试、跨进程 txn ID 唯一性。

`test_transactions_windows.py` 覆盖：intent 提交与成功清理、查询状态、恢复策略与幂等、未知文件保留、跨进程 `LockFileEx`（writer 阻塞 / 恢复器 busy）、并发 txn ID 唯一性。

`artifacts/acceptance/lock_threads.c`：同进程真实多线程竞争（S2）。直接调用导出给 MoonBit 的 C 锁原语 `moondelta_lock_table`/`moondelta_unlock_table`（即 `acquire_shared_lock` 与 `try_acquire_exclusive_lock` 的实现），用线程覆盖独占互斥、共享共存、busy 可见、释放后获取、句柄/槽位不泄漏与固定锁文件不被替换。POSIX 用 `-pthread` 由 CI 编译运行；Windows 侧已用 mingw gcc 编译并记录（`artifacts/acceptance/transaction-2026-11-12-review/lock-threads-windows.log`）。

`artifacts/acceptance/powerloss/test_verifier.py`：验收器自身的正反例。除结构类损坏（截断 commit、缺数据文件、intent 摘要冲突、日志缺口）外，还包括**同长度 payload 篡改、Schema 变更、数据文件摘要不符**，以及“伪造 delta-rs 行数”“缺少内容对照的轮次”必须被判 FAILED。需要 `deltalake`/`pyarrow`。

`artifacts/acceptance/powerloss/test_recover_interrupts.py`：S3 恢复器自身中断矩阵（仅 POSIX）。用 `src/powerloss_probe.c` 在 `cleanup-unlinked` / `cleanup-dir-fsynced` 边界定点阻塞并 SIGKILL，随后重复 `recover --apply` 收敛，断言只删归属明确的临时文件、既有文件逐字节不变、双引擎读回一致、二次 apply 无删除、恢复后仍可写入。这是进程崩溃证据，不是掉电证据。

`artifacts/acceptance/transaction-2026-11-12-review/check_verifier_gaps_closed.py`：把 2026-11-12 复验发现的两处漏检转成回归断言（同长度篡改必须被拒、伪造行数必须判 FAILED）。`reproduce_verifier_gaps.py` 与 `verifier-gap-results.json` 保留为当时的原始记录，修正后该脚本的“漏检仍存在”断言按设计会失败。

`d4_structure.py`、`d4_v3_check.py`、`links_hashes.py` 是 2026-10-20 口径补丁的**历史校验器**，其断言绑定当时文本；文档再次修订后不代表当前验收结果，不应作为现行门槛。

依赖：DuckDB delta 扩展（首次运行自动 INSTALL/LOAD）。脚本末尾会写 `.out` 文件；如果目录只读，检查结果仍会打印到 stdout，但进程会以权限错误退出。

## 6. CI

`.github/workflows/ci.yml`：安装最新 MoonBit 工具链 → `moon update` → check/test/build → 验收器自检与漏检回归 → 同进程多线程锁矩阵（POSIX）→ Linux 事务集成矩阵 → S3 恢复器中点中断矩阵；Windows runner 单独执行 Windows 原子发布/锁/恢复矩阵与同一组验收器回归。本地基线：Linux 与 Windows Native 均 56/56，JS/Wasm 静态检查 0 errors。当前提交 `fa4c2eb` 的远端 CI（run 43160975199）`check-test-build` 与 `windows-check-test` 均成功：<https://github.com/xiguaAp6y3/moondelta-core/actions/runs/43160975199>。

`.github/workflows/s5-powerloss.yml`：S5 掉电矩阵的手动入口（`workflow_dispatch`，固定 `ubuntu-24.04`，`timeout-minutes: 300`），依次执行依赖安装、KVM/loop 能力探针、guest 内核与 initramfs 构建、离线自检、前置门禁、边界 trace、100 轮切断矩阵，并始终上传产物与读取器二进制。`rounds < 100` 会被降级为 `INVALID`。**2026-11-12 两次实跑**：run 43157333594 通过但断言不核对内容（保留为历史）；补齐内容一致性门槛后 run 43176818126 重跑通过，100/100 PASS、`failed=0`、`invalid=0`，每轮核对 Schema/行值/数据文件摘要并双引擎逐行对照（证据见 `artifacts/acceptance/powerloss/ci-2026-11-12-content/`）。
