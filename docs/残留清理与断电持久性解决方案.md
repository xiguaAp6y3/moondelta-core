## 1. 目标和现状

当前 Native 写路径已使用同目录临时文件、文件同步及不覆盖的硬链接发布；本轮补齐 Linux 父目录同步和日志已发布后同步失败的结构化错误。尚缺可持久识别的事务归属、结果查询恢复及与活跃 writer 互斥的清理机制。现有 WSL 测试验证的是进程中断、I/O 注入和发布竞争；不能据此宣称断电持久性。

本轮目标：

1. 中断事务的临时文件和未提交数据可自动、安全、重复清理；历史版本仍可读取。
2. 在通过验收的 Linux 本地文件系统上，成功返回的提交在模拟断电恢复后仍存在，且其引用的数据完整。
3. 发布结果不确定时返回明确状态，调用方可查询恢复，禁止盲目重复 append。
4. 正式 Delta JSON 与 Parquet 仍遵守现有 reader 1 / writer 2 格式，不要求外部 reader 理解本项目维护元数据。

## 2. 清理设计

### 2.1 先证明文件归属，再删除

新增隐藏维护目录 `.moondelta/`，只供本项目 writer 与清理器使用。每次写操作生成 OS 随机 transaction ID；数据文件名改为含该 ID 的唯一名称，取代仅依赖时间戳的唯一性假设。每个事务持有一个不可变 intent 清单，记录格式版本、事务 ID、目标版本、临时文件和正式数据文件的相对路径、预期长度与提交内容摘要。恢复不依赖可被写到一半的可变状态字段。

清单必须在任何被管理文件创建前完整写入、原子发布并同步到目录。临时路径预先确定，使用排他创建，数据和日志临时文件仍位于各自目标文件的父目录；不得先创建临时文件再追记清单。清单发布自身中断时，数据写入尚未开始，只可能遗留维护目录内的清单临时文件。

对历史遗留文件：旧 `*.moondelta-tmp-*`、Windows `mdt*.tmp` 和旧 `part-*` 文件没有充分归属证据，默认只报告，不凭文件名批量删除。在确认表完全停写的维护窗口，可由显式迁移清单纳入管理。未知文件、软链接、目录、越界路径及清单格式错误均保留并报告。

### 2.2 与 writer 协调

采用一个固定 inode 的表级维护锁，不在解锁时删除或替换锁文件：

- `create_table` / `append_rows` 从创建 intent 前到提交持久化或失败处理结束，全程持共享锁。共享锁允许多个 writer 继续竞争版本。
- 清理器只能非阻塞取得独占锁后执行；锁忙则自动清理跳过，显式命令返回 `busy`。
- Linux 使用 `flock`；Windows 使用固定字节区间的 `LockFileEx`。同一进程内的多个调用也必须纳入互斥验证，不能只测跨进程。
- 锁句柄不得被子进程意外继承；进程退出后由操作系统释放。不得用 PID 存活检查、mtime 或租约超时替代互斥证明。

本项目之外的 writer 不遵守该锁。因此，引擎可混合读写的普通 Delta 表默认只执行 dry-run，不自动删除。只有用户明确启用“本项目管理的写入目录，全部写入方遵守维护锁”策略后，才能自动删除；否则仅在外部 writer 已停止的维护窗口执行。该策略限制的是自动维护，不限制 Delta reader 互操作。

### 2.3 删除判定和步骤

取得独占锁后，完整验证 intent，再从日志和 checkpoint 建立保护集合。保护集合包括可保留历史中的 `add`、`remove` 路径及受支持的相关数据引用；不只取最新快照。初版采用保守规则：只要文件在可见历史或 checkpoint 中出现过，就不由此清理器删除。真正的历史 VACUUM、日志过期和历史数据回收另行实现。

初版删除未引用正式 Parquet 的前提是能证明创建以来日志完整连续；截断日志、checkpoint-only、解析失败或未知引用类型均不删除正式 Parquet。历史证据不足不能被解释成“无引用”。仅有 checkpoint 的表仍可按现有能力读取，但该清理器拒绝推断旧文件归属。

执行顺序：

1. 非阻塞取得独占维护锁，重新读取最新日志状态；锁覆盖整个枚举、判定与删除过程。
2. 收集有效 intent；校验所有相对路径规范化后仍在表内，拒绝软链接跳转和路径别名冲突。
3. 若 intent 对应正式 commit 已存在，比较摘要及数据引用；确认已提交的文件永久排除，冲突版本引用了该事务的数据时也必须保留。
4. 对已结束事务，只删除清单列出的临时文件；正式数据文件还必须不在保护集合中。长度不符等异常先报告，不能扩展删除范围。
5. 完成删除后同步被修改的父目录；最后移除 intent 并同步维护目录。删除失败或同步失败保留 intent 供下次恢复，不清空证据。
6. 已删除文件再次遇到 `ENOENT` 视作幂等完成。清理失败不得让已经提交的 append 被误报为未提交。

旧正式数据与保留历史文件不自动回收；年龄阈值可以用来降低清理频率，但不是安全依据。

### 2.4 API 与自动触发

已新增 `recover_table(root, dry_run=true)` 与 CLI `delta recover <root> [--apply]`（以及 `delta query`、`delta manage`），返回候选/删除/保留数量、路径与理由、锁忙/日志不完整/外部 writer 策略阻止等结果。

已启用受管策略的表，在首个 writer 操作前尝试一次恢复；失败安全跳过或报告，不偷偷降级为强制清理。append 成功后可尝试清理本事务临时文件；进程重启后的下一次恢复负责遗留 intent。读操作不触发删除。不新增常驻后台服务。

## 3. Linux 持久化提交顺序

文件同步不足以保证父目录中的新名称持久化；Linux 手册要求显式同步父目录。因此目标顺序固定如下，任何前置同步失败均不得继续发布 commit：

1. 创建表目录、`_delta_log`、维护目录时，逐级同步承载新目录项的父目录；正确支持绝对路径，并明确符号链接路径策略。
2. 持久化 intent：写完整清单 → `fsync(file)` → 不覆盖发布 → `fsync(intent_parent)`。
3. 写临时 Parquet → 完整写循环 → `fsync(data_fd)` → `link(temp, final)` → `fsync(data_parent)`。这一步成功前不能发布 JSON。
4. 写完整临时 JSON → `fsync(log_fd)` → `link(temp, N+1.json)` → `fsync(_delta_log)`。
5. 第 4 步的目录同步成功后，才返回提交持久化成功。正式 JSON 的硬链接创建仍是读可见的线性化点，两者必须在文档中区分。
6. 删除临时名称并同步相关目录；删除 intent 放在数据/日志已持久化之后。尾部清理失败作为维护警告，不撤销已持久化提交。

为降低 unlink 修改 inode 后的歧义，首次目录同步前保留临时名；同步完成后再移除临时名并再次同步父目录。文件、目录句柄关闭及同步错误都必须检查；禁止忽略 EIO/ENOSPC 或使用全局 `sync` 掩盖缺失的必要同步。

初版强持久性支持范围仅为经测试的 Linux Native + 本地 ext4 配置；要求底层存储正确实现 flush/barrier。NFS、SMB、FUSE、WSL `/mnt/e`、macOS 和 Windows 不自动继承该结论。

## 4. 日志已可见后的错误与恢复

Native FFI 不应再只有一个混合 errno 结果；至少携带阶段、是否已发布目标、平台错误码及事务 ID。建议公开错误：

| 状态 | API 语义 | 调用方处理 |
|---|---|---|
| 发布前失败 | `IoError` / `DurabilityUnsupported`，没有该事务的正式 commit | 检查并恢复残留后可重试 |
| 目标版本被占用 | `CommitConflict` | 读取最新快照，使用新事务重试 |
| JSON 已发布，但目录同步失败或结果未知 | `CommitOutcomeUnknown(txn_id, version, path)` | 查询事务清单与 commit 摘要，禁止盲目重放 |
| JSON 已发布且同步成功，清理失败 | 返回提交成功，另报维护警告 | 后续恢复重试清理 |

恢复时，intent 和目标 commit 匹配就认定该事务已可见；在目标文件与目录同步重新成功前，不将其升级为“已确认持久化”。目标版本属于其他事务时返回冲突；无 commit 且历史完整时可认定未提交。不能靠“version >= 目标版本”判断本事务已成功。

`txn_id` 用于本项目写入恢复，首版不宣称提供通用 exactly-once API；需要跨请求幂等时另行增加调用方 operation ID 与查询接口。未知结果恢复期间不得回滚或删除正式 commit。

## 5. Windows 单独验收

现有 `FlushFileBuffers` 加 `CreateHardLinkW` 不能直接作为本项目已验证的目录项持久性证据。Windows 事务清单、受管维护锁（固定锁文件句柄 + `LockFileEx`、不可继承、进程退出释放）、结构化发布结果和进程中断/跨进程测试已补齐（`artifacts/acceptance/transaction-2026-11-11/`）；Windows 临时文件使用含事务 ID 的本项目专属名称。

对 NTFS 的名称发布持久性，另做官方 API 与文件系统行为验证及虚拟机断电试验，未完成前保留“进程中断一致性”能力；请求强持久性时在创建数据前返回 `DurabilityUnsupported`，禁止静默回退。不得承诺一次普通目录句柄 flush 就等价 Linux 的目录 fsync；也不把需要管理员权限的卷级 flush 作为默认写入前提。

## 6. 测试与验收门槛

| 组别 | 必须加入的测试 | 通过条件 |
|---|---|---|
| 清理归属 | 部分临时数据、完整未引用数据、临时日志、已提交但 intent 未删除、旧命名文件、未知文件 | 只删除证明属于已结束事务的文件；已提交和未知文件保留 |
| 活跃写入 | writer 暂停在数据发布前后、JSON 发布前后，同时启动恢复；同进程多线程、多进程 | 活跃 writer 不被删，恢复锁忙有明确结果；reader 始终可读 |
| 历史保护 | remove 后仍被旧版本使用的文件、checkpoint、截断日志、损坏日志、percent 编码路径 | 历史 time travel 不受影响；历史不全时禁止删除正式数据 |
| 恢复幂等 | 清理每一步再次强杀，重复 recover；外部 writer 策略未开启 | 恢复可重复执行，不越界、不误删；未授权自动维护只 dry-run |
| 同步错误 | 对每个必要的 file/directory fsync 注入 EIO/ENOSPC，另测不支持目录同步 | 数据目录失败不发布日志；日志已发布后返回 OutcomeUnknown；不误报持久化成功 |
| 原子可见性 | 实际读取 worker 与 delta-rs 在提交前后连续查询；同一版本固定文件和逐值结果 | 只有旧版或完整新版；已发布版本内容不变化 |
| 同版本竞争 | 两 writer 都到达 JSON 发布前屏障后才放行，重复 100 轮；失败方恢复后重试 | 恰好一成功一冲突、内容不覆盖，重试可形成下一完整版本 |
| 断电模拟 | 专用 QEMU Linux guest + 可丢弃的 ext4 数据盘，在持久化步骤边界切断 guest 存储/电源模型，重启恢复 | 已确认成功的版本永不丢失；未确认的事务允许旧版或完整新版；不允许可见日志引用缺失/部分数据 |

注入点不再需要另建 `atomic_write_gate.c`：`src/powerloss_probe.c` 已插在 `moondelta_publish_pinned`/`moondelta_unlink_sync` 的系统调用边界（17 个边界，见 `artifacts/acceptance/powerloss/boundaries.json`），由 `MOONDELTA_POWERLOSS_AT` 定点通告并阻塞，未启用时空转，不影响正常提交路径。SIGKILL、正常关机、`wsl --terminate` 都不能单独证明断电持久性。断电 harness 必须说明如何丢弃尚未 flush 的设备缓存、如何保留已完成 flush 的写入；只杀 QEMU 而保留宿主脏页缓存也不足以作为唯一证据。装置（volatile NBD 缓存模型、最小 guest、100 轮编排器、主机侧校验器）已齐并通过离线自检，仍待在合格 Linux host 上实跑取证。

测试基线：每个 syscall/同步边界至少覆盖一次；磁盘级随机崩溃至少 100 次，保存随机种子和镜像配置。每次验证日志连续性与可解析性、版本、引用文件存在性/长度/摘要、schema、行数与逐字段值；使用本项目与 delta-rs 双读。成功确认记录保存在独立控制端，区分未收到成功确认与已收到成功确认的事务。

清理测试使用独立临时目录；断电测试使用专属虚拟机与可丢弃磁盘，不对宿主机或共享 WSL 发行版做强制断电。

具体路线、当前状态、执行任务和每阶段退出门槛统一维护在[事务验收路线图](S1-S5事务验收路线图.md)，本节仅保留阶段总览。
