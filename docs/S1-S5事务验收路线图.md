# S1–S5 事务验收路线图

日期：2026-11-10（2026-11-11 更新 S2/S3 实现状态；2026-11-12 更新 S5 实跑结果）。状态：S5 已在指定 CI 配置下通过 100 轮（run 43157333594）；完整事务验收的其余门槛见文末表格。

## 验收终点

本路线图关闭 Delta reader 1 / writer 2 基线下的本地 Native 事务一致性问题。成功提交必须在数据及其目录项持久化、JSON commit 及其目录项持久化之后才返回成功；中断恢复不能改变已提交快照、删除仍被历史版本引用的数据，或把无法判定的事务当作可安全重放。读者只读标准 Delta 日志和 Parquet；本项目维护数据放在 Delta 目录之外部不可见的 `.moondelta/`。

进程崩溃、I/O 故障、原子可见性、清理恢复和掉电持久性分开验收。前四项通过不能替代掉电试验。支持声明必须限定到有证据的操作系统、文件系统、内核、设备缓存模型和 writer 实现。

## S1：提交持久化边界

**交付物**

- 明确两个时点：正式 JSON `link` 是新版本对 reader 可见的线性化点；JSON 父目录同步成功才允许向 writer 返回已确认提交。
- POSIX Native 写入按序完成：数据临时文件完整写入和文件 `fsync` → 不覆盖发布 → 数据父目录 `fsync` → JSON 临时文件完整写入和文件 `fsync` → 不覆盖发布 → `_delta_log` `fsync`。
- 数据目录同步失败时不发布 JSON；JSON 已可见但目录同步失败时返回 `CommitOutcomeUnknown(path, errno)`，保留可见 commit，不允许调用方将其当作普通发布前错误盲目重放。
- 建表目录逐级同步；必要同步重试 `EINTR`；提交成功后的临时名清理失败不改变已确认提交结果。

**当前证据**：WSL2 Ubuntu 24.04、Linux 6.6.114.1、发行版 ext4；S1 轮次的 18 个 syscall/建表故障及调用顺序断言通过，当时 Native 单测 39/39（2026-11-11 扩展后全仓为 56/56，见 [最新事务复验](../artifacts/acceptance/transaction-2026-11-11/README.md)）。S1 原始记录见 [事务复验记录](../artifacts/acceptance/transaction-2026-11-10/README.md) 与 `results.json`。

**退出门槛**：所有必要同步点有成功顺序断言和 EIO/ENOSPC/EINTR 结果断言；数据持久化失败不产生正式 JSON；日志发布后的同步失败明确是 unknown；发布后维护清理错误不伪报 append 失败。Windows 不继承 POSIX 持久性结论。S1 的代码/注入部分满足；S5 前不宣称断电持久性。

## S2：事务身份、intent 与互斥

**交付物**

1. 为每次建表/append 生成操作系统随机事务 ID；POSIX 使用可靠随机源，Windows 使用系统加密随机源。禁止用时间戳、PID、计数器或文件名碰撞概率作为唯一性证明。
2. 在创建事务数据前，原子持久发布不可变 intent，至少包含格式版本、事务 ID、目标版本、临时与正式相对路径、预期长度、数据摘要、JSON commit 摘要。intent 文件先同步，再同步 `.moondelta/` 目录。路径预先确定且采用排他创建。
3. 数据文件名包含事务 ID。原子发布接口接受 intent 预先记录的临时路径，避免 C 层随机生成的临时名未被归属清单覆盖。Delta JSON action 仍使用标准相对路径，不暴露自定义 action。
4. 完成锁契约：writer 从 intent 创建前持共享锁到提交已确认或失败状态已记入；recoverer 用非阻塞独占锁。POSIX 固定 `.moondelta.lock`、`flock`、`O_CLOEXEC`、拒绝 symlink 已有初步实现；补同进程多调用/多线程和多进程测试。Windows 实现固定锁文件句柄和 `LockFileEx`，验证子进程不继承锁句柄。锁文件绝不 unlink 或替换。
5. 扩展 unknown 错误和只读查询 API，返回 txn ID、目标版本、路径和阶段。查询必须比较 intent 摘要与正式日志内容；匹配后重新同步相关文件/目录才可升级为确认持久。目标版本被其他事务占用为 conflict；日志不连续、摘要不匹配或 intent 损坏返回 unresolved，不能推断未提交。

**当前证据（2026-11-11，本机）**：`src/txn.mbt`（intent/查询）、`src/atomic_file_native.c`（固定临时名发布、随机源、POSIX `flock`、Windows `LockFileEx`）已实现；`src/delta_wbtest.mbt` 的 56 个原生单测在 Linux 与 Windows 各 56/56 通过，覆盖 200 次 txn ID 唯一性、同进程多句柄共享/独占互斥、intent 残留下的 committed / committed-unconfirmed / not-committed / conflict / unresolved 查询。Linux 集成脚本用 8 个并发进程与相同 payload/timestamp 验证 OS 随机 ID 不碰撞，用 Python `flock` 与 worker 组合验证锁忙与释放，并让 writer 暂停在数据发布之后、JSON link 之前时启动恢复器，确认只能得到 busy 且活跃 intent/数据未被删除；Windows 独立脚本用 `ctypes` 持有 `LockFileEx` 独占/共享锁，验证 writer 阻塞、恢复器 busy；Windows 查询在摘要匹配后保持 `committed-unconfirmed`，不把文件同步冒充目录项持久性。新增覆盖：`add.path` 最小 percent-encoding 的跨引擎 `remove` 匹配、真实 commit-unknown 结果的 `query_transaction` 复核。**未覆盖**：真实多线程共享进程的拍发（现以同进程多句柄调用等价覆盖）、远端 CI、S5 断电；Windows 仅证明进程崩溃一致性，不证明 NTFS 名称/断电持久性。

**测试与退出门槛**

- 事务 ID 唯一性测试覆盖并发创建、进程重启和相同调用 timestamp；每个 intent 发布步骤注入中断后都能解析或保守保留。
- 一个进程内两个独立锁句柄、多线程、多进程竞争均验证 writer 共享/恢复独占互斥；writer 在数据发布、JSON 发布前后暂停时，recoverer 只能得到 busy，不能看到或删除活跃事务文件。
- 对 JSON 已可见但目录同步失败、同版本被其他 writer 赢得、intent 存在但无 commit、intent 已提交未清理分别验证查询结果。
- POSIX 与 Windows 各自运行本平台锁和进程退出释放测试；未实现的平台不得返回“锁已获取”的语义。

**禁止推进条件**：intent 不是先于 managed data 持久化；ID 可碰撞/不可恢复；同一进程锁语义未实测；恢复无法区分本事务 commit 与同版本其他事务。任一项存在时 S3 不得删除文件。

## S3：安全恢复和清理

**交付物**

- 提供 `recover_table(root, dry_run=true)` 及 `delta recover <root> [--apply]`。结果列出候选、将删除、保留、锁忙、日志不完整、未知文件和外部 writer 策略阻止等路径与原因。
- 默认 dry-run。只有用户明确将表标记为“全部 writer 遵守 moondelta 维护锁”的受管表才允许自动 apply；混合外部 writer 的 Delta 表永远只预览，除非调用者明确选择停写维护窗口的 apply。
- 持独占锁后读取并校验全部 intent，再构造历史保护集合。只要任一可保留 JSON 历史或受支持 checkpoint 引用某路径，该数据文件永久受本清理器保护；初版不做 VACUUM。
- 正式未引用 Parquet 仅在 intent 明确归属、日志从版本 0 连续可解析、无 checkpoint/未知引用歧义、文件路径/长度/摘要吻合且不在历史保护集合时可删。截断/缺失日志、checkpoint-only、损坏 intent、符号链接、路径越界、路径别名和未知文件一律保留并报告。
- 只删除 intent 精确列出的临时文件和被证明未引用的正式文件；不按通配符清旧 `part-*`、旧 `.moondelta-tmp-*`、Windows `mdt*.tmp`。先删数据并同步父目录，最后删 intent 并同步维护目录；步骤可重入，`ENOENT` 幂等，其他错误留下 intent。
- 受管 writer 在操作开始前尝试一次非阻塞恢复独占锁；取得后完成恢复并释放，再获取 writer 共享锁。若锁忙则不清理、不等待维护操作，并按 API 策略报告/跳过。成功提交后可清理本事务临时名，intent 清理失败不改变已提交成功语义。

**当前证据（2026-11-11，本机）**：`src/recover.mbt` 与 CLI `delta recover|query|manage` 已实现。单测覆盖 intent-only、数据已发布未提交、commit 已发布未清理、历史保护、日志缺口、损坏 intent、未知/旧命名文件、锁忙、重复恢复幂等与受管 writer 操作前自动清理；Linux 集成覆盖 SIGKILL 残留恢复、dry-run/受管 apply、历史保护、日志缺口、未知文件保留、恢复 unlink 失败后保留 intent 并可重复清理收敛；Windows 脚本覆盖 dry-run/策略/apply/幂等与未知文件保留。新增覆盖：真实 `remove` 后旧版本仍可读、有效单文件 checkpoint 引用保护、checkpoint-only 与多部分 checkpoint/不支持协议只报告不删除、percent 编码路径解码保护、软链接保留、恢复失败重试收敛。**未覆盖**：掉电、远端 CI、真实多线程拍发。

**测试与退出门槛**

- 构造中断在 intent 前后、部分 Parquet、数据发布后、JSON 临时写入后、JSON 发布后和 intent 删除前；重复恢复结果稳定，最终只删归属明确且不受保护文件。
- 构造 remove 后仍被旧版本使用的数据、有效 checkpoint、checkpoint-only、日志缺口/损坏、percent 编码路径、未引用且归属明确数据、未知文件和软链接；逐版本 time travel 与 delta-rs 读回不变。
- 在恢复每个 unlink/fsync 边界再次 SIGKILL，重启重复 recover；并发 reader 始终看到完整快照，writer/恢复器互斥可靠。
- 默认配置与混合 writer 表只能 dry-run；只有显式受管表才能自动清理。回归报告必须证明没有删除旧命名文件。

**禁止推进条件**：仅凭文件年龄、命名模式或最新快照判断垃圾；历史不完整仍删除正式 Parquet；apply 无维护锁；提交成功被清理失败改报失败；历史读回发生变化。任一项存在时 S3 不通过。

## S4：集成回归与验收证据

**现有基线**：23 项故障注入（20 个 syscall/intent + 3 个建表）、intent 先于数据的同步顺序、SIGKILL 部分写入与残留恢复、100 轮正式 JSON 发布前竞争/连续 reader/冲突重试、外部 delta-rs 对照、POSIX/Windows 维护锁阻塞与 symlink 拒绝、dry-run/受管 apply/历史保护/日志缺口/未知文件保留/跨进程 txn ID 唯一性/writer 暂停时恢复器 busy/清理失败重试均通过；Linux Native 56/56，Windows Native 56/56，JS/Wasm 静态检查 0 errors。证据见 [2026-11-11 事务复验](../artifacts/acceptance/transaction-2026-11-11/README.md)。远端 CI 尚未运行。

**阶段交付**：把 S2/S3 场景合入现有 `artifacts/acceptance/test_atomic_commit_wsl.py` 或相邻验收脚本；保留逐 syscall trace、随机种子、事务 ID、结果文件和源码 SHA-256。CI 在 Linux runner 构建 worker、运行完整故障/清理/race 矩阵并上传 artifacts；推送后实际观察一次远端成功结果。Windows runner 独立执行 Windows 原子发布、锁与恢复支持矩阵，不用 WSL 结果替代。

**退出门槛**：干净全仓 build/check/test；POSIX 与 Windows 各自受支持能力的测试全过；清理、互斥、历史保护、恢复幂等案例全过；CI artifacts 可复核；已知不支持能力在 API/README/申报中一致标识。失败场景必须被证明触发，不能仅由测试环境中“未发生错误”判通过。

## S5：掉电持久性与平台结论

**环境交付**

- 专用 Linux VM 和可丢弃的 raw ext4 数据盘；记录 QEMU、guest kernel、ext4 feature/mount、虚拟控制器、cache/discard 配置、host 文件系统及测试脚本版本。
- 本仓库提供前置门禁与验收规则：`artifacts/acceptance/powerloss/README.md`、`check_environment.py`；当前环境输出 `BLOCKED`，不得把门禁脚本存在或 `/dev/kvm` 存在当成掉电 harness 已就绪。先建立 disposable VM 和块设备故障注入，确认模型会丢未 flush 写、保留已完成 flush 的写。仅杀 QEMU 进程但 host page cache 最终仍落盘，不足以证明掉电语义。
- 装置已按上述要求实现，待合格 host 实跑：`volatile_nbd.py`（易失写缓存 + 协议级正反向自测）、`prepare_raw_ext4.py`（可丢弃数据盘）、`mk_initramfs.py` + `guest/init`（最小 guest）、`src/powerloss_probe.c`（`MOONDELTA_POWERLOSS_AT` 定点通告并阻塞，插入 `moondelta_publish_pinned`/`moondelta_unlink_sync` 的系统调用边界）、`boundaries.json`（17 个边界，9 个必需）、`run_powerloss.py`（100 轮编排：QEMU→NBD 顺序 SIGKILL、逐轮 fsck/只读挂载/校验）、`verify_round.py`（主机侧结构校验与双引擎读回）、`selfcheck.py`（离线自洽检查）。离线部分已通过，实跑与取证仍缺。
- 独立控制端记录每次事务发起、返回成功/unknown、txn ID 和序号；断电后控制端记录不能与 guest 虚拟盘一起丢失。

**执行矩阵**

1. 在临时 Parquet 写、文件 fsync、数据 link、数据目录 fsync、JSON 临时写、JSON fsync、JSON link、日志目录 fsync、intent 清除等持久化边界随机切断 guest 电源/块设备；至少 100 次，保存随机种子与每轮注入位置。
2. 恢复后检查日志连续、每个正式 JSON 可解析、commit 引用文件存在且长度/摘要正确、快照版本/Schema/行值正确；分别用项目 reader 和 delta-rs 读取。
3. 已收到“提交成功”的事务必须存在且完整；未收到成功确认的事务允许不存在或作为完整新版本存在，但不允许空/半截 commit、缺失引用文件、版本读回变化。unknown 事务按查询恢复语义核对。
4. 对同一 QEMU cache 和设备模型先跑正向控制用例（已确认 flush 可恢复），再跑掉电注入；若模型未证明丢弃未 flush 写，整组结果判无效，不可写成 PASS。
5. Windows NTFS 单独建立支持结论：若不能构造可信掉电与名称持久化证据，公开标记“强持久性不支持/未验证”，不将 Windows `FlushFileBuffers` 进程测试升级为断电保证。

**退出门槛**：100 次有效断电模型运行满足上述不变量，所有失败有可解释且已修复的原因后，才可声明该精确 Linux VM/ext4/设备配置的强持久性。随机断电、配置和日志证据缺失时 S5 不通过；其他文件系统、macOS、WSL `/mnt/*`、NFS/SMB/FUSE 不因该结果自动纳入支持范围。
